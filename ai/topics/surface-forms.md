# Surface forms in non-Kio' files

Trigger: editing a `.kio` file.

Kio' is the small, intrinsic-bearing core; the full surface language layers operators, tuple literals, `.stem. { ... }` placeholder lambdas, `alias` literal aliases, label sugar, UFCS, and imported elaborator calls (including the block forms `if!`, `scope!`, `do!`, and `match!`) on top of it. When a file is *not* Kio' (i.e., it does not parse against the Kio' grammar in [`specs/prime.md`](../../specs/prime.md)), prefer the surface form to the Kio' equivalent it elaborates to:

- No `import __intrinsics__;` and no direct `__intrinsic__` calls. Use operators, tuple literals, spine elaborators, `match!`, `if!`/`else`, etc.
- For value coercions, reach for the right elaborator. Prefer the spine palette for ordinary surface code: `widen_sum!` / `widen_prod!` (widen), `narrow_sum!` / `narrow_prod!` (narrow), `reorder_*`, `flatten_*`, `one_*`, and `fit!` for composed coercions. Use the algebraic palette (`iso!`, `into!`, `onto!`, `align!`, `ease!`) when the file is specifically exercising those forms or the algebraic rule is the subject. `atom!` is the exception in that palette: reach for it freely to pick a single value from an aggregate — that everyday case is ordinary surface code, not subject-gated (see the `atom!` guidance below) — and reserve the subject-gating only for `atom!`'s broader DNF-flatten-to-a-nonobvious-arm generality.
- Sum elimination goes through `match!`, not `__either__` or hand-rolled `__if_then_else__` chains.
- Product construction is the tuple literal `(a, b, …)`, not `__pair__`.
- Sum construction is `widen_sum!(e)`, not `__left__` / `__right__` (except when the goldens' subject is the intrinsic itself).
- Conditionals use imported `if!` with its `else` block, not `__if_then_else__`; use `scope! { … }` for an ordinary scoped sequence and `do! bind { … }` for bind-based sequencing.

The exception is when the file's *subject* is the intrinsic (e.g., a golden whose point is to assert the intrinsic typechecks, builds, or executes — `build_intrinsics`, `typecheck_intrinsics`). Those cases keep the direct intrinsic usage; what they're testing is the Kio'-level form. A second flavor of the same exception: any golden that carries an `IS_KIO_PRIME` marker is *required* to be valid Kio' — the marker is biconditional (see `ci/checks/per-case/prime-marker.sh`), so introducing a surface form into a regular-module *.kio file inside such a case removes the marker, narrowing the corpus the Kio' verifier validates. When the case's subject is Kio'-level typechecking, building, or execution (`typecheck_rec_deftypes`, `typecheck_existentials`, `exec_panic`, `build_sum_elimination`, …), the intrinsic stays.

**Use the coercion elaborator's explicit-target form for inline coercions.** The coercion elaborators below accept a trailing target type: `widen_sum!(e, T)`, `narrow_prod!(e, T)`, `fit!(e, T)`, etc. The palette is split in two: the **spine** forms (`reorder_sum!` / `reorder_prod!` / `narrow_sum!` / `narrow_prod!` / `widen_sum!` / `widen_prod!` / `flatten_sum!` / `flatten_prod!` / `one_sum!` / `one_prod!` / `fit!`) and the **algebraic** forms (`iso!` / `into!` / `onto!` / `align!` / `ease!` / `atom!`). When the expression's surrounding context doesn't pin the type (a `let` RHS, an arg in a generic call), pass the target explicitly inline. **Do not** introduce a one-off helper fn (`fn mk_left(s: String) -> (String | !) { widen_sum!(s) }`) just to anchor the expected type — the inline `widen_sum!(s, (String | !))` is shorter, keeps the test's intent local, and avoids polluting the module with a wrapper. Helper defns are warranted when they capture genuine reuse, not when they exist solely as type-annotation scaffolding.

**Single-elaborator coercions use the axis-specific form; multi-elaborator coercions use `fit!`.** Each spine form (`reorder_sum!` / `reorder_prod!` / `narrow_sum!` / `narrow_prod!` / `widen_sum!` / `widen_prod!` / `flatten_sum!` / `flatten_prod!` / `one_sum!` / `one_prod!`) covers exactly one axial operation. When a coercion does one thing — permute, drop, widen, flatten an outer axis, or pick — name that thing: `narrow_prod!((a, b, c), (a, c))` over a hand-built composition. When a coercion needs more than one — narrow on one axis while widening on another, or recurse through nested products and sums — reach for `fit!`, which composes the narrow-before-widen discipline, recurses on slots, and walks function arrows contravariantly/covariantly. Composing axis-specific forms by hand (`narrow_prod!(widen_sum!(e, T), U)`) is discouraged when `fit!(e, U)` would produce the same result; the composer reads better and lets the engine validate the multi-axis story end to end.

**Prefer UFCS for blockless elaborator calls.** A blockless elaborator can have a receiver-first UFCS spelling: `r.>iso!` for `iso!(r)`, `r.>into!(T)` for `into!(r, T)`, `r.>onto!(T)` for `onto!(r, T)`, `r.>align!(T)` for `align!(r, T)`, `r.>ease!(T)` for `ease!(r, T)`, `r.>atom!` for `atom!(r)`, `r.>narrow_prod!(T)` for `narrow_prod!(r, T)`, `r.>fit!(T)` for `fit!(r, T)`, and so on across the blockless palette (see [`specs/language.md` § UFCS](../../specs/language.md#ufcs)). The parens-iff-args UFCS rule applies to those calls: omit the list when there is no trailing target type argument, because an explicitly empty UFCS list is rejected; write `(())` only for an additional Unit value. Write the UFCS form when the receiver is the natural focus of the expression — typically when it is a single name or a short expression that reads better at the head of the line. Block calls use their direct form, such as `match! value { clauses }`; they do not have a blockless UFCS spelling. Same exception as above: when the file's *subject* is the standalone bang-call form being parsed, lowered, or rejected, keep the original spelling.

**Prefer UFCS for type-member access.** Write `r.>T.member` over `T.member(r)` when `T.member` takes a single value-arg that the receiver fills (see [`specs/language.md` § UFCS](../../specs/language.md#ufcs)). Same exception applies — keep `T.member(r)` when the test's subject is the projector/constructor call form itself.

**`let _ = e;` is an antipattern; use the expression-statement form instead.** Kio block bodies admit both `LetStmt` (`let name = e;`) and `ExprStmt` (`e;`). The expression-statement form discards `e`'s value directly — the typer requires `e : .`, which most side-effecting calls already produce. Write `print(s); print(rest)` (a sequence of two statements followed by the trailing expression `print(rest)`), not `let _ = print(s); print(rest)`. The bound name `_` carries no information, the `let` adds visual noise, and the surrounding code reads less clearly. Use `let _ = e;` only when `e`'s type is genuinely non-unit and you need to deliberately discard the value — those cases are rare.

**Prefer elided type-arguments when inference can fill them — and prefer fuller elision.** Kio infers type arguments from the finite application-local relation between value arguments, connected nested applications, and the surrounding expected type (see [`specs/language.md` § Type-argument inference and the `_` placeholder](../../specs/language.md#type-system)). When the typer can solve a type-arg from those sources, drop it: write `id(x)` rather than `id(T, x)`, `Box.mk_box(v)` rather than `Box.mk_box(T, v)`, `push(x, xs)` rather than `push(T, x, xs)`. There is a **preference ladder**, most to least preferred — for `fn f[A](A) -> A` called on a string: (1) `f("")` — omit the type-arg slot entirely (the goal); (2) `f(_, "")` — explicit `_` placeholder, only when the slot must be positionally present but its type is still inferable; (3) `f(String, "")` — explicit type, only where inference genuinely can't (a rare phantom-type case). Reach down a rung only when the rung above doesn't type-check; `f("")` is the nullary-elided spelling of `f(_, "")` (same call, fewer slots written). The exception is cases whose *subject* is the explicit type-arg path itself (e.g., `exec_infer_placeholder` exercises three call shapes side-by-side, `exec_qualified_poly_call` pins the type-arg-through-qualified-import path, `exec_fn_hash` uses an explicit type-arg to pin a placeholder lambda's expected type). `kio fmt` enforces this one-directionally: it NEVER de-elides (`f("")` must not become `f(_, "")` / `f(String, "")`); contracting `f(_, "")`→`f("")` is optional (see [`specs/style.md`](../../specs/style.md)).

**Don't introduce a alias as a call-arg type-arg workaround.** Compound types `(A & B)` / `(A | B)` are valid in every type-arg position, including the trailing target slot of `iso!` / `into!` / `onto!` / `align!` / `ease!`. A alias is justified by reuse or by giving a domain concept a name (`Cnf`, `Dnf`, `Lens`); it is not justified by "the slot can't carry a compound type" — that is never a constraint.

**Prefer `atom!` only for picking a single value from an aggregate.** `atom!(e, T)` (or its target-elided form `atom!(e)`) is the focused elaborator for "extract a single value of type `T` from this aggregate." The common case is single-component projection from a record / product: `r.>atom!(Field)` picks the generated label type from a product, or `pair.>atom!(T)` picks the `T`-typed component from a product. `if!`/`else` and `match!` already return the common arm type directly; don't add `atom!` just to collapse their result.

`atom!`'s target must DNF-normalize to a single arm (atom, nominal, or product); a multi-arm sum target is a type error. An atomic source is admitted as a degenerate identity, but a plain reference reads better than `a.>atom!(A)` for that case — reach for `atom!` when there's actually something to pick from.

Use the axis-specific spine elaborator (`narrow_sum!`, `widen_sum!`, `fit!`, etc.) for sum narrowing, widening, or other length-changing rearrangements. Same exception as above: when the file's *subject* is a broader algebraic elaborator being parsed, lowered, or rejected, keep the original spelling.

**Repeated same-typed sum arms should usually be named, not hand-injected.** `into!` is deterministic across like-typed sum arms via the source-order rule (see [`specs/language.md`](../../specs/language.md) § Anonymous sum and product types, *Commutativity*): the kth source DNF branch of type `T` maps to the kth target slot of type `T`. So `into!(100, (I32 | String) | I32)` always lands the `I32` in the *leftmost* (inner) `I32` arm. For ordinary source, that is a signal to introduce labels/newtypes for the domain alternatives, or to write the example so the target branch is identified by type. Do not solve routine modeling ambiguity by importing `__intrinsics__`.

If a focused test must construct a non-leftmost like-typed structural arm, make that test's subject explicit: it is exercising Kio' / intrinsic construction, not ordinary surface authoring. Keep any raw intrinsic usage confined to that intrinsic-focused case; castles, docs examples, and natural goldens should use labels, `widen_sum!`, and `match!` unless the user explicitly asks for the core form itself.
