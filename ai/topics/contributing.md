# Contribution-policy mirror set

Trigger: editing `CONTRIBUTING.md`, anything under `.github/ISSUE_TEMPLATE/`, `.github/PULL_REQUEST_TEMPLATE.md`, `.github/workflows/pr-auto-close.yml`, `.github/workflows/pr-policy-check.yml`, `.github/workflows/contrib-run.yml`, or `test-data/contrib/README.md`.

The policy in one line: **bug reports are the primary contribution; contributed cases under `test-data/contrib/` are the one accepted PR shape; everything else is maintainer-only, with an issue labeled `accepting prs` as the rare maintainer-invited exception.**

These seven surfaces describe the **same contribution policy** to different audiences, and a change to one almost always implies changes to the others:

- `CONTRIBUTING.md` — the long form, linked from the GitHub "Contributing guidelines" prompt. Canonical for the policy itself.
- `.github/ISSUE_TEMPLATE/*` — what a reporter sees when filing a bug report, reserving a contrib case, or floating a feature idea.
- `.github/PULL_REQUEST_TEMPLATE.md` — what a contributor fills in when opening a PR.
- `.github/workflows/pr-auto-close.yml` — the automation that closes unsanctioned PRs.
- `.github/workflows/pr-policy-check.yml` — the immediate PR status check: classifies a PR, mirrors the sanctioning label onto it (`contrib case` / `accepting prs`), validates the contrib directory naming and file-level contract (commenting on failures), warns on a `run.sh` case, and strips the `test-contrib` run approval on every push.
- `.github/workflows/contrib-run.yml` — the maintainer-triggered runner: on the `test-contrib` label (applied only by someone with write access), builds and runs the one contrib case at the approved commit under a per-job timeout. This is the only place a contrib PR's code executes before merge.
- `test-data/contrib/README.md` — the contrib-lane case contract, enforced mechanically by `ci/checks/orchestrators/contrib-tests.sh`.

Before finishing a change to any of them, open the others and confirm they still agree. Typical propagations:

- **Acceptance policy** (bug-reports-first; the contrib lane as the only accepted PR shape; `accepting prs` as the maintainer-invited exception) — touches every audience surface. The issue templates shape what a reporter writes, the PR template tells a contributor what to link, `CONTRIBUTING.md` is the canonical statement, and the two closing/classifying workflows enforce it: `pr-auto-close.yml` and `pr-policy-check.yml` must encode the same sanction rules (contrib path prefix + linked issue; `accepting prs` label).
- **Contrib-lane shape** (the `<github-username>-<issue#>` directory naming, the touches-only-`test-data/contrib/` rule, the links-an-issue rule) — `test-data/contrib/README.md` is canonical for the case contract; the naming and path rules also appear in `CONTRIBUTING.md`, the "Contribute an example program or library" issue template, the PR template, `pr-auto-close.yml`'s path check (`contribPrefix`), and `pr-policy-check.yml` (which constructs the expected directory name from the PR author + linked issue and checks a file-level subset of the contract). All must agree, and the contract validation in `contrib-tests.sh` must enforce the same shape the README states. The **file allowlist** (only the fixed control files plus `workdir/`; only `.kio` under `workdir/`; no symlinks) is a security boundary — keep it identical in `contrib-tests.sh` (`validate_contrib_contract`) and `pr-policy-check.yml`, since an external PR is untrusted until merged.
- **Reproducer shape** ("attach a minimal `.kio` file") — `CONTRIBUTING.md` and the bug-report template both name it; they must agree. Neither promises the file lands anywhere verbatim — it's a maintainer who turns a report into a regression test.
- **Grace-period or trigger changes** in `pr-auto-close.yml` — the "auto-closed after …" wording in the PR template and `CONTRIBUTING.md` § What happens to other PRs must match the actual workflow behavior.
- **Case shapes** (exactly one of `run.args` for a program, `run.test-only` for a library — which requires an `equiv` law — or a maintainer-reviewed `run.sh`; no other `*.sh`), the **bug-reproducer mechanism** (`KNOWN_FAILING` marks an expected failure that stays green but warns, enforced in `ci/run-tests.sh`; `pr-policy-check.yml` advises on it), the **`test-contrib` run flow** (maintainer-only label; stripped on push; `run.sh` advisory), and **owner-only follow-ups** (`pr-policy-check.yml` requires the case-dir owner prefix to equal the PR author) — `test-data/contrib/README.md` is canonical; `contrib-tests.sh`'s validator, `pr-policy-check.yml`'s allowlist + naming + advisories + strip, and `contrib-run.yml`'s trigger + permission gate must all agree. The execution-file contract (`run.args` / `run.sh` / `run.test-only`, exactly one) also lives in `ci/run-tests.sh`'s `assert_case_run_contract`.

When proposing a CONTRIBUTING.md change, list the mirror-set updates as part of the same proposal — don't propose the canonical change first and discover the templates separately. [`audit-github`](../skills/audit-github/SKILL.md) § 2 sweeps for residual drift and checks `pr-policy-check.yml` accepts every valid case; [`audit-corpus`](../skills/audit-corpus/SKILL.md) § 8 tracks the corpus's `KNOWN_FAILING` cases as open bugs. But the cheaper path is to keep the mirror set in step as you write the change.
