# Repository layout

Pointer: read when navigating the repo or adding new top-level files / directories.

- [`DESIGN.md`](../../DESIGN.md) — language goals and design rationale; specifications remain the behavioral authority. The whole design is protected by AGENTS.md § Universal rules — Project design is approval-gated.
- `AGENTS.md` — the always-loaded entry point. Universal rules, the trigger table, and the pointer set.
- `ai/` — AI-tooling subtree. `ai/topics/` holds the topic files referenced by `AGENTS.md`'s trigger table and pointer set — agents navigate here on demand, and AGENTS.md is the complete index (no orphan topics). `ai/skills/` holds the Markdown-defined agent skills, exposed to Claude Code via the `.claude/skills` symlink. Structural integrity of the topic-file system is enforced by [`ai/skills/audit-agents-md/SKILL.md`](../skills/audit-agents-md/SKILL.md).
- `README.md` — public entry point on GitHub. `ROADMAP.md` — public-facing index of in-flight design threads. `CONTRIBUTING.md` — contribution workflow, full DCO text. `TESTING.md` — testing strategy and "where does my new test go" decision tree; operational reference lives in `test-data/README.md`.
- `.github/` — CI workflows, issue/PR templates, `CODEOWNERS`. `workflows/ci.yml` runs monthly (first day at 06:00 UTC) and on `workflow_dispatch`: ordinary Linux runs use `ci/all.sh SAMPLE_IMPL --sample-cases` plus the fixed dynamic-Prime smoke set, with independent full-implementation and full-case manual opt-ins; macOS / Windows run one sequential portability job per OS including the scheduler's native self-test and crate tests. Other workflows: `devcontainer-publish.yml` (monthly rebuild of the dev container image on GHCR), `pages.yml` (manual Pages deploy via `workflow_dispatch`), `markdown-link-check.yml` (weekly), `pr-auto-close.yml` (weekly sweep + PR events), `pr-policy-check.yml` (PR events), `contrib-run.yml` (maintainer-triggered contrib-case runner, on the `test-contrib` label), `stale.yml` (weekly), and the version-tag release channel — `release.yml` (cargo-dist-generated release builds for `**[0-9]+.[0-9]+.[0-9]+*` tags, plus pull-request planning), `publish-crate.yml` (crates.io publish on `releases/v*` tags), and `publish-vscode.yml` (Marketplace and Open VSX publish on `releases/v*` tags). The issue and PR templates and the three contribution workflows mirror `CONTRIBUTING.md`'s contribution policy — see `ai/topics/contributing.md` for the mirror set.
- `.devcontainer/` — the dev container source: `Dockerfile`, `devcontainer.json`, lifecycle scripts (`on-create.sh`, `update-content.sh`, `post-attach.sh`) and the helpers they call (`refresh-kio.sh` builds the binary the editor's language server runs; `find-code-cli.sh` resolves the VS Code CLI that installs the extension), `README.md`. See [`ai/topics/local-tools.md`](local-tools.md).
- `.markdownlint.json`, `.yamllint` — linter configs; see `ci/checks/repo-lint/`.
- `ci/` — code (POSIX shell scripts, Rust crates, JS driver) for the gating checks and the test harness. Runnable locally as `sh ci/all.sh SAMPLE_IMPL` and from `workflows/ci.yml`. Top-level entrypoints sit at the root of `ci/`: `ci/all.sh` (the gating orchestrator), `ci/run-tests.sh` (the case-runner harness), `ci/watch-builds.sh` (a local continuous `kio-rs` build warmer), `ci/cargo.sh` (the Cargo wrapper shared by CI scripts, with optional scheduler-native `KIO_CI_SERIALIZE_CARGO=1` serialization), `ci/impl-toolchain.sh` (selects CI implementation shards and installs their backend toolchains), `ci/regenerate-builtin-docs.sh` (regenerates the checked-in builtin-module reference from the compiler's builtin metadata), and `ci/schedule.sh` (the thin shell-facing facade for the native work, Cargo, and compiler scheduler). Everything else is organized under two umbrellas: `ci/checks/` for gating verdicts and `ci/infra/` for the sources and scaffolding the harness consumes:
  - `ci/checks/orchestrators/` — gating jobs that drive a target (corpus or subproject) end to end: corpus sweeps (`golden-tests.sh`, `emissions-tests.sh`, `generative-tests.sh`, `poc-tests.sh`, `castle-tests.sh`, `contrib-tests.sh`, `kiodoc-tests.sh`, `highlight-tokens.sh`, `highlight-agreement.sh`, `lsp-tests.sh`, `smoke-reports.sh`, `vscode-e2e.sh`, `builtin-docs.sh`, `fmt-canonical-tree.sh`, `fmt-comment-conservation.sh`, `rust-output-determinism.sh`, `runner-cache-hermeticity.sh`, `website-e2e.sh`). The `lib/` subdirectory contains sourced helpers such as `common.sh` and the emissions contract validator, not gating buckets: orchestrators source them by paths derived from their own locations. `ci/all.sh`'s non-recursive discovery (`find … -maxdepth 1 -name '*.sh'`) never runs `lib/` as a job.
  - `ci/checks/per-case/` — per-case check scripts (`fmt-canonical.sh`, `dep-canonical.sh`, `prime-marker.sh`, `kio-prime-roundtrip.sh`, `rlib-cache-second-run-hits.sh`, `warm-recheck-stable.sh`, `tsc-strict.sh`, `pyright-strict.sh`) invoked by `ci/run-tests.sh --check=`. These are *sub-checks* — they produce per-case verdicts but are not standalone gating jobs.
  - `ci/checks/repo-lint/` — repo-config linting that doesn't touch Kio: `sh-lint.sh`, `markdown-lint.sh`, `github-lint.sh`, `version-check.sh`, `license-check.sh`, `skill-frontmatter.sh`, `backend-api-stability.sh`, `golden-reference-deps.sh`, `emissions-corpus.sh`, `dep-materialization.sh`, `dep-canonical-selftest.sh`, `equiv-discharge.sh`, and focused self-tests for the structural contract checks. Golden/generated-host placement remains a manual review because shell dataflow is not a repository-lint concern.
  - `ci/checks/hygiene/` — per-crate cargo fmt/clippy/test scripts, one file per Rust crate in the repo: `kio-rs.sh` for the main implementation, `kio-repl-wasm.sh` for the browser-REPL wasm wrapper crate, and `kio-ci-scheduler-rs.sh` / `kio-gen-rs.sh` / `kio-prime-check-rs.sh` / `kio-test-runner-rs.sh` for the support crates under `ci/infra/`. A new Kio compiler lands here as `<impl>.sh`.
  - `ci/infra/` — the support-crate sources consumed by the harness: `kio-ci-scheduler-rs/` (the work/Cargo/compiler resource engine, compiler capacity policy, native process supervision, and bootstrap behind `ci/schedule.sh`), `kio-gen-rs/`, `kio-prime-check-rs/`, `kio-test-runner-rs/`, `native-compiler-proxy.sh` (the custom-`run.sh` compiler-admission dispatcher), plus `highlight-agreement-js/` (the Node.js driver for the three-way highlight-agreement check).

  `ci/all.sh` orchestrates every gating script for local dev and for the Linux GitHub sampled gate; each gating script is also independently invokable. `ci/all.sh` auto-discovers gating scripts across those three buckets (excluding `checks/per-case/`), so adding a new gating check means placing the script in the right bucket. The macOS / Windows workflow job is an explicit portability subset; add a script there only when that check needs hosted-runner OS coverage.
- `reports/` — POSIX shell scripts for **reporting** harnesses. Runnable locally as `sh reports/all.sh` (umbrella) or `sh reports/<name>.sh` directly. Sibling to `ci/`, not a child: `ci/` holds gating scripts that block merge on failure; `reports/` holds analyses whose output is information for human triage, not a gating signal. Today: `mutation.sh` (cargo-mutants over the semantic core: typer, elaborator registry, substitute pass, evaluator/normalizer, and Prime path, with bounded exploratory and authenticated deterministic-campaign modes), `fuzz.sh` (cargo-fuzz over the parser and lexer; nightly Rust), `kio-gen-coverage-delta.sh` (cargo-llvm-cov coverage delta for generated cases), and `equiv-eval-reachability.sh` (a direct, non-gating LLVM source locator used deliberately when auditing evaluator-test confidence). The first three are driven by their corresponding `audit-*` skills; the evaluator locator remains directly invokable rather than becoming a per-change gate.
- `specs/` — authoritative specifications; see [`ai/topics/specs.md`](specs.md) for the file-by-file list.
- `docs/` — pedagogical material for Kio (tutorials, topic guides, host integration guides); see [`ai/topics/docs.md`](docs.md).
- `kio-rs/` — Rust implementation of Kio (Cargo project): compiler and CLI. Package name `kio-rs`, binaries `kio` and `kio-prime` (see [`ai/topics/implementation.md`](implementation.md)). The `fuzz/` subdirectory is a separate cargo-fuzz crate (`kio-rs-fuzz`, `publish = false`) holding the libFuzzer targets for `reports/fuzz.sh` — its own workspace, requires nightly Rust to build.
- `kio-repl-wasm/` — Rust/wasm wrapper for the browser REPL inspector. Builds a `wasm-bindgen` `cdylib` over `kio-rs`'s `repl-core` feature and embeds the POC corpus for the website landing-page inspector.
- `website/` — VitePress static site. Build scripts derive docs pages from `docs/README.md` plus `kio doc build --html`, derive the host-language list from `specs/backends/*.md`, build the `kio-repl-wasm` bundle into VitePress public assets, and publish through the Pages workflow.
- `test-data/` — Kio source and fixtures consumed by CI: cross-implementation goldens under `test-data/goldens/`, backend-specific public-host and durable-artifact evidence under `test-data/emissions/`, highlight fixtures at `test-data/highlight-corpus/`, Kiodoc cases at `test-data/kiodoc-cases/`, adopter-grade POCs at `test-data/poc/`, composed-program castles at `test-data/castles/`, and community contributions at `test-data/contrib/`. The harness, per-case checks, orchestrators, and support crates all live under `ci/`. Strategy is in [`TESTING.md`](../../TESTING.md); operational contracts are in [`test-data/README.md`](../../test-data/README.md) and [`test-data/emissions/README.md`](../../test-data/emissions/README.md). **Goldens are language-level fixtures, not implementation tests**: case-owned code never inspects, transforms, imports, or native-compiles generated host-backend files, and comments use spec/language vocabulary rather than implementation names. A golden may hand opaque artifacts to a documented fixed runner protocol; Kio' is the specified backend-neutral phase-artifact exception. Emission cases are one-backend `HOST_INTERFACE` or `ARTIFACT_SHAPE` evidence and never substitute for cross-backend runtime coverage or private unit/mutation tests.
- `LICENSE-MIT`, `LICENSE-APACHE` — dual-licensed under MIT or Apache-2.0 at the user's option, mirroring the Rust project's convention.
