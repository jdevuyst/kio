# Agent instructions

Read this file first: it is the repository's source of truth for agent instructions.

Update `AGENTS.md` alongside changes to project conventions, goals, or tooling.

## About Kio

Kio is an ultra-portable, embeddable language based on polymorphic lambda calculus with higher-kinded types. It transpiles to other languages.

Kio is designed to be:

- **Hosted** — Kio packages are components that run inside a host language/runtime, not standalone programs. The host supplies the package's capabilities (numerics, strings, I/O, …) and decides which exposed package entries to invoke.
- **Dynamically loadable** — alongside compile-time linking, hosts can load pre-compiled Kio programs at runtime. The interface stays statically typed, so type errors are caught at compile time.
- **Developer-friendly** — great diagnostics, fast feedback loops, and first-class tooling are part of the design contract, not afterthoughts.

Formal guarantees the language commits to: sound, decidable type system; strongly normalizing Kio' core; open-world compilation.

## What belongs in AGENTS.md vs. `ai/topics/<topic>.md`

AGENTS.md is the always-loaded entry point. It contains only:

- **Universal rules** — compact rules that every conversation needs before its first action. A rule here carries its full norm — every must, never, and gate — and none of the extended rationale; the why, the catalogues, and the war stories live in the owning topic file (or in `TESTING.md` / `CONTRIBUTING.md` where those are the natural home).
- **The trigger table** — a `(action → topic file)` mapping. Before taking a listed action, read the linked topic file. Triggers must be **sharp** (something recognizable from a tool call's arguments before execution, e.g., "before editing a `.kio` file"). Fuzzy triggers ("before designing a feature touching X") are a sign the rule should stay in the universal core.
- **The pointer set** — on-demand reference catalogues (`ai/topics/repo-layout.md`, `ai/topics/local-tools.md`, …). The agent navigates to these when working in the area.

Put conventions needed before every conversation's first action here as compact norms, never multi-paragraph rules. Put the rest in topic files with triggers or pointers. [`audit-agents-md`](ai/skills/audit-agents-md/SKILL.md) checks this split and size.

`audit-agents-md` enforces structural integrity: `AGENTS.md ≤ 40,000 characters`, every trigger and pointer resolves to a real file under `ai/topics/`, every `ai/topics/<topic>.md` file is referenced from `AGENTS.md` (no orphans), and cross-references from tracked files of the form `AGENTS.md § …` still resolve.

## Universal rules

These rules apply to every change in this repo. Read them before the first tool call.

- **Project design is approval-gated.** Follow all of [`DESIGN.md`](DESIGN.md) in proposals and implementations. Creating, editing, deleting, renaming or departing from it requires explicit user approval of that specific change; general task authority is insufficient. Never rewrite it to justify a conflict. Behavioral-contract authority and scope rules still apply.
- **Open-world compilation is non-negotiable.** Adding new declarations to a `*.kio` module body must never cause a different module to fail to compile or change its meaning. This is a hard rule, not a guideline. The formal statement lives in [`specs/language.md` § Open-world design](specs/language.md#open-world-design) and [`specs/formal/prime.md` § 7. Open-world](specs/formal/prime.md#7-open-world); the pitfall catalogue and design checklist in [`ai/topics/open-world.md`](ai/topics/open-world.md). When sketching a feature that touches name resolution, imports, dispatch, or inference, **state the open-world argument explicitly**.
- **Behavioral contracts cannot be rewritten retroactively.** Before implementation, a normative change to accepted or rejected programs, name resolution, inference, visibility or capabilities, specified diagnostic behavior, phase trust, or another public contract must be uniquely authorized. The **authority baseline** is the relevant specification at the start of the user-requested unit of work, before any agent-authored spec or implementation edit for that work. The **effective authorized contract** is that baseline plus specific user-authored instructions or approvals given before implementation that deliberately supersede or settle it. A delegated task inherits only the authority it cites; delegation cannot create or broaden authority. Splitting work across commits, branches, worktrees, sessions, or agents does not reset the baseline, and a spec whose own authority is disputed cannot authorize follow-on work. Current implementation behavior, a new test, an audit or review finding, and a same-work spec edit are evidence, not authority. If unauthorized implementation already exists, isolate or revert it from the landable range, present the contract decision, and only then proceed as newly authorized work; after-the-fact approval does not erase the violation or waive fresh review, tests, specs, docs, or other gates. Details the effective contract explicitly leaves incidental, unspecified, or evolving remain implementation choices. An exit-code category map does not imply precedence: unless a command-specific contract explicitly says otherwise, input with multiple independent errors is selected deterministically but may report any applicable diagnostic and category, and a public conformance test that pins one category isolates that defect.
- **Backend decisions propagate by semantic applicability.** Whenever backend behavior is authored or reviewed, or a backend-local defect exposes a design rule, state the backend-neutral semantic law and classify it at the narrowest truthful level: universal; a capability cohort that may cross family boundaries; genuinely family-common only after every member's evidence agrees; or backend-specific host syntax/integration. The discovery backend, its declared family, and its current mechanism never determine scope by themselves. Before claiming completion, give every applicable current backend and semantically distinct occurrence an explicit applicability, conformance, and evidence result; place shared policy, planning code, specs, tests, and audit gates at that semantic level, with per-backend pages and emitters recording only their realizations. Details: [`ai/topics/emit.md`](ai/topics/emit.md) § Decision record and propagation gate; normative placement: [`ai/topics/specs.md`](ai/topics/specs.md) § What goes into a backend spec.
- **Findings do not broaden scope.** Classify each finding before fixing it: (1) a regression introduced by the current authorized work; (2) a pre-existing defect whose required behavior follows uniquely from the effective authorized contract and is necessary for the current work or explicitly included in its user-authorized scope; (3) an unrelated pre-existing defect; or (4) a contract or design ambiguity. Repair or revert (1) before the current work lands; isolate (2) as a narrow, separately reviewable batch; report (3) for the user to schedule, without modifying code or trackers unless that tracking is already authorized; and stop for a user decision on (4). A failing test, audit finding, review rejection, or the no-partial-implementations rule never turns (3) or (4) into authorization.
- **Disproportionate machinery is a design-stop signal.** When a narrow or obscure behavior starts requiring cross-cutting implementation machinery out of proportion to its contract, stop before expanding it and present the concrete complexity, affected phases, state and performance costs, and simpler contract or architecture alternatives. Green tests and sunk work do not waive this checkpoint, and the checkpoint never authorizes an agent to simplify or otherwise change the behavioral contract.
- **User declarations never become compiler primitives by name.** Except for grammar forms and reserved intrinsics explicitly authorized by the specification, compiler behavior follows ordinary resolved and typed language structure. Never grant typing, lowering, evaluation, visibility, control-flow, or capability semantics by matching a user-spellable bare name, comparing against a compiler-hard-coded or otherwise distinguished ordinary-library identity, or treating declaration spelling, grouping, producer provenance, or raw source argument indices as substitutes for resolved semantic slots. This does not prohibit generic use of the identity the program actually resolved: exact capture/visibility-edge validation, nominal equality, ordinary dispatch, host linking and backend naming, diagnostics, and caching all depend legitimately on resolved identities without singling out a compiler-known library declaration. Kio-authored elaborators are ordinary imported declarations: changing `match` to a hard-coded fully qualified identity would not make a `match!` special case sound. If required behavior is not expressible from ordinary structure, stop and present a general structural mechanism or an explicitly authorized language construct; do not smuggle the behavior through a library-name hook. The detailed implementation and evidence rules live in [`ai/topics/implementation.md`](ai/topics/implementation.md) § User declarations are not syntax.
- **Builtin modules are approval-gated.** Do not add or revise declarations, exports, constructors, helper entries, or other surface area in builtin modules such as `__intrinsics__` or `__comptime__` unless the user has explicitly approved that builtin-module change.
- **`ROADMAP.md`, `README.md`, `CONTRIBUTING.md`, the crate and extension listing READMEs, the landing page, the blog posts, and the GitHub contribution templates are approval-gated.** Do not create, edit, or delete any content in `ROADMAP.md`, `README.md`, `CONTRIBUTING.md`, the crates.io and Marketplace listing READMEs (`kio-rs/README.md` and `tools/vscode-kio/README.md`), the website landing page (`website/.vitepress/theme/components/Landing.vue`), the hand-written blog posts under `docs/blog/` (the post `.md` bodies only — the blog build pipeline, index generation, and styling are ordinary code and not gated), or the GitHub contribution templates (`.github/ISSUE_TEMPLATE/`, `.github/PULL_REQUEST_TEMPLATE.md`) unless the user has explicitly authorized that specific change — even when a task seems to imply or require the edit, propose the change and get a yes first. Unlike the rest of `docs/`, blog posts are written by hand by the maintainers, not AI-generated. They are project-defining, high-visibility files; the trigger-table topics ([`ai/topics/roadmap.md`](ai/topics/roadmap.md), [`ai/topics/readme.md`](ai/topics/readme.md), [`ai/topics/contributing.md`](ai/topics/contributing.md)) and the listing-README rules in [`audit-readme`](ai/skills/audit-readme/SKILL.md) still apply, but reading them is not sufficient.
- **Blog post bodies have their own publication context.** Hand-written `docs/blog/*.md` post bodies are exempt from the no-leak rule and may link to any tracked path in this repository, including the agent-guidance layer. A GitHub link from a post to a repository file or directory must use `blob/<full-commit-id>/…` or `tree/<full-commit-id>/…`; a moving branch or tag such as `main` is forbidden. The blog linter and [`review-blog-post`](ai/skills/review-blog-post/SKILL.md) enforce this rule. A CI failure never authorizes editing a post, including its hidden harnesses, or preserving language compatibility by default; report the conflict for a maintainer decision. Blog examples remain subject to current-compiler validation; details live in [`ai/topics/docs.md`](ai/topics/docs.md) § Blog posts.
- **Kio' is a strict subset of Kio.** Every spelling, identifier class, declaration or import form, typing rule, and runtime meaning admitted by Kio' must also be admitted with the same meaning by the full Kio pipeline. Kio' narrows Kio by rejecting surface forms; it never adds Prime-only syntax, AST cases, capabilities, or compiler-generated exceptions. Lowering may synthesize only ordinary constructs from that shared subset. [`specs/prime.md`](specs/prime.md) and [`specs/grammar.md`](specs/grammar.md) must document this boundary; any spec or implementation production or privilege that violates it is a bug, not an exception. [`audit-prime-grammar`](ai/skills/audit-prime-grammar/SKILL.md) and [`audit-surface-forms-survival`](ai/skills/audit-surface-forms-survival/SKILL.md) check both directions.
- **Surface forms must not survive into Kio'.** Implementations of the surface language must remove every non-Kio' surface form before the AST reaches Kio' (the post-typecheck phase); a backend may run further *post-typecheck* passes on the strict Kio' AST — those introduce no surface forms and don't bear on this rule. The pass that removes a given form is an implementation choice; when removal needs information only available later, the typer records the elaboration in a boundary-local side channel and a substitute pass swaps the recorded form in at the Lowered → Prime boundary. Which forms need this, and the pass inventory: [`ai/topics/implementation.md`](ai/topics/implementation.md); authoring discipline: [`ai/topics/surface-forms.md`](ai/topics/surface-forms.md).
- **Calls are typed from their resolved types, never declaration side channels.** Once a callee is resolved, call completion, argument grouping, partial application and residualization, and UFCS placement derive only from its public type, the written call syntax, and local type constraints. Declaration parameter grouping, runtime ABI arity, callee identity or provenance, and a user elaborator's private implementation ABI may bind a body or gate execution only after that public call plan is fixed; they must never change the call's accepted syntax or inferred type. Details and counterfactual checks: [`ai/topics/implementation.md`](ai/topics/implementation.md) § Retained application inference.
- **Phase artifacts cannot inherit authority from their producer.** The meaning and authority of a Prime, serialized, cached, emitted, reparsed, or dynamically loaded artifact must follow from its phase representation plus validator-checked explicit dependencies — never from a reserved spelling, a claim that the compiler generated it, or provenance outside the artifact. Fresh textual compiler input is validated as untrusted input; a cache may memoize completed validation but cannot grant authority absent from the validated artifact. The runtime `dyn_load_prime` loader is the documented precompiled-artifact boundary: it trusts function-body typing and validates only its structural and host/export-contract edges, so successful loading is not full artifact validation. Do not claim that runtime loading re-typechecks bodies. Reserved names provide hygiene, not privilege. If an authorized private edge remains represented past lowering, its representation must use ordinary constructs from the Kio'/Kio shared subset, carry only narrow evidence, and let the receiving phase rederive or verify that exact edge; it must not widen one selected member into module-wide access. This rule does not decide that such an edge belongs in Prime: compiler-only transient states may instead be consumed before the persistent phase boundary. The detailed boundary test is in [`ai/topics/implementation.md`](ai/topics/implementation.md); [`audit-surface-forms-survival`](ai/skills/audit-surface-forms-survival/SKILL.md) checks it.
- **Compile-time evaluation observes phase boundaries.** `equiv`, `:normalize`, user elaborators, templates, and future `__comptime__` hooks must reduce Kio'-shaped core terms (`UncheckedPrime` while compile-time holes are still explicit, `Prime` after validation) plus an explicit primitive environment — never Lowered/surface ASTs, hidden typer state, or cross-boundary side channels. Downstream phases consume only their phase artifact; the full phase-boundary purity story is in [`ai/topics/implementation.md`](ai/topics/implementation.md).
- **Function purity is not declaration purity or phase purity.** `pure` is admitted only on an ordinary `fn` and constrains executable value references in its body, never its signature or type annotations; types have no purity class. A user-elaborator implementation always executes purely regardless of the `elab` spelling: a named implementation and every ordinary helper it reaches are `pure fn`s. An implementation declared in the elaborator's defining module may remain private, and private transitive helpers are allowed under ordinary same-module visibility. A cross-module target must be ordinarily importable into that defining module but need not meet the elaborator's outward visibility; only captures carry that floor. After bang-call substitution, standalone Prime validation checks the generated term under the caller's retained function-purity contract. Details: [`specs/language.md`](specs/language.md#module-system) and [`ai/topics/implementation.md`](ai/topics/implementation.md) § Function purity versus phase-boundary purity.
- **Language changes move the whole surface together.** A change to syntax, grammar, static semantics, lowering, reduction/normalization, or any user-visible language behavior must update affected specs and docs in the same change, with the impact argument stated explicitly over the consumer checklist in [`ai/topics/language-surface-tooling.md`](ai/topics/language-surface-tooling.md) — parser, formatter, the Kio' verifier, `equiv` / `:normalize`, `kio-gen-rs`, syntax highlighting, LSP, the VS Code extension, and `kio sig` (the host-contract changelog; see [`specs/versioning.md`](specs/versioning.md)). "No impact" is acceptable only when justified from the changed boundary; do not land a code-only semantic change.
- **Host-backend API stability is explicit and approval-gated.** Each backend spec/guide pair has exactly one matching `Host API stability: evolving|stable`; new backends start `evolving`; Kio' is excluded. Promotion, demotion, and each compatibility break require explicit approval. `stable` also requires an earlier published demotion before any break; `evolving` grants no standing break authority. The field classifies compatibility only and gives no quality, correctness, completeness, performance, conformance, caveat, or acceptance relief. See the [contract](specs/backends/README.md#host-api-stability) and [workflow](ai/topics/specs.md#what-goes-into-a-backend-spec).
- **No partial implementations.** When a change closes a tracked issue, fix the whole issue relative to its authorized contract — don't land a slice that handles the easy case, leave the hard case as residual behavior, and call the issue closed, and don't expand the contract merely to make the issue larger. A genuinely incremental slice is fine only when the commit message says so and the tracker stays open; a doc comment never converts a partial fix into a complete one. The exception is behavior the spec deliberately omits — state the spec rule, not the implementation gap. [`audit-partial-implementations`](ai/skills/audit-partial-implementations/SKILL.md) sweeps for violations.
- **Per-backend limitations: only the genuinely impossible, mutual-cited.** Shipping backends implement the whole Kio contract; specs/guides carry no backend version, maturity tier, or experimental label. Host API stability covers compatibility only. A concrete known break may be disclosed only in matching top banners in `specs/backends/<lang>.md` and `docs/hosts/<lang>.md`; disclosure accepts no limitation, excuses no fixable bug, and grants no implementation, test, conformance, or acceptance relief. A new backend with any caveat fails `add-backend` acceptance: stop and surface it. A carve-out or accepted limitation requires proof that the host cannot express a spec- or IR-admitted case after every escape hatch — never an engineering-effort choice; fix every expressible gap in IR, codegen, or runtime. An unexercised shape is *undetected, not unsupported*: its missing golden is a bug; a guarded/fallible/catch-all emitter identity/pass-through for a constructible admitted case is a partial implementation. Every accepted limitation has the matching banners plus an emitter-site comment citing the spec section. Full-contract family divergence instead uses no banner and the mutual cite in [`specs/backends/README.md`](specs/backends/README.md) § Language families. Citations do not prove impossibility: [`audit-spec-drift`](ai/skills/audit-spec-drift/SKILL.md) § 7 requires manual discharge against [`ai/topics/emit.md`](ai/topics/emit.md) § The escape hatch; [`audit-partial-implementations`](ai/skills/audit-partial-implementations/SKILL.md) § Silent guard / catch-all fallthrough and [`audit-backend-family-conformance`](ai/skills/audit-backend-family-conformance/SKILL.md) check mechanics.
- **Bugs surface; never hide them.** When tests expose a violation of the effective authorized contract, fix the bug rather than hide it. A test for one side of an unresolved design question is proposal evidence, not a regression test, and cannot decide the contract. **Bug-exposing goldens stay in place**: deleting or skipping the case or removing an applicable target from its `build { ... }` block is forbidden regardless of session scope. If the fix cannot land, keep the failing golden, use the error-bucket layout in [`TESTING.md`](TESTING.md) where applicable, and surface the gap; a should-pass runtime case retains a `run.sh` comment naming the bug. The resource-only dynamic stress exception in [`TESTING.md` § Stress and semantic coverage](TESTING.md#stress-and-semantic-coverage) requires a reasoned skip marker, bounded cost evidence, retained compact dynamic semantic coverage, and unchanged applicable backend stress coverage; it never excuses an interpreter defect. **Each bug fix lands with a minimal, dedicated regression golden** exercising the exact bug, not incidental coverage in a larger case. **Observe that regression fail against the unfixed code before landing**: revert the fix, observe the failure, and restore it. Verify that the test actually executes its subject and its assertion can fail; a vacuous green result is not coverage.
- **Goldens demonstrate behavior, not workarounds.** Goldens are cross-implementation language, diagnostic, runtime, and public-API tests. A fixed independent runner protocol that uses only the documented host interface is the default public-API oracle. Case-owned code never reads, copies, greps, patches, imports, or native-compiles a generated host-backend file; it may hand an opaque output directory to that runner. Kio' is the backend-neutral phase-artifact exception: a golden may directly read or assemble Kio' when that artifact or the dynamic-load boundary is its subject, and generic harness-owned phase checks remain valid. Generated-host evidence that the ordinary runner cannot naturally and independently demonstrate, plus durable filesystem evidence, belongs under [`test-data/emissions/`](test-data/emissions/README.md); private no-filesystem invariants belong in unit or mutation tests. A golden's Kio source shows what a user would naturally write; when a backend fails to build or run it, fix the emitter rather than reshaping the source with inference-dodging annotations, monomorphic substitutes, or alias scaffolding.
- **Optimizations are justified, not assumed.** A change defended as a performance optimization must either change observable language/runtime output (and so be golden-pinned) or carry a **recorded measurement** of its win at land time; and it must have firing coverage at the truthful layer: a golden for language/runtime behavior, an `ARTIFACT_SHAPE` emission case for a durable measured or specified generated-host fact, or a unit/mutation test for a private invariant. Complexity justified only by an unmeasured "it's faster" does not stay. Firing / no-op is swept by [`audit-mutation`](ai/skills/audit-mutation/SKILL.md); the measured-win discharge by [`audit-compiler-performance`](ai/skills/audit-compiler-performance/SKILL.md) § 8 Optimization justification.
- **Checked-in files are written for outside readers — keep them context-free.** Outside the hand-written `docs/blog/*.md` post bodies, never leak session-, machine-, or maintainer-specific detail — scratchpad or sibling-worktree paths, box specs, a user's identity or private rationale, agent-orchestration mechanics, session-relative dates — into any tracked file; the repo must read the same on every machine and for every maintainer. The leak-class catalogue and the portability filter live in [`ai/topics/no-leak.md`](ai/topics/no-leak.md); [`audit-no-leak`](ai/skills/audit-no-leak/SKILL.md) sweeps for violations.
- **Scratchpads require approval.** Never create a new `scratchpad/` file unless the user authorizes it. Use the configured temporary root; see [`ai/topics/scratchpad.md`](ai/topics/scratchpad.md) for existing files.
- **Aspirational content lives only in `ROADMAP.md`.** Public-facing artifacts — `specs/`, `docs/`, README-class pages, agent instructions, user-facing CLI output — never name an unbuilt feature, promise later support, or defer work to the future: no "future extension" notes, no "not yet supported", no "planned X". State the current contract in the present tense — what is accepted, what is rejected, what does not exist — and, for a deliberate boundary, why it sits where it does. Reservations stated as current rejections, concrete current-caveat banners, forward-compatibility contracts, policy conditionals, and the exact Host API stability field remain admissible — they constrain the present rather than promise. Backend maturity and ad hoc stability banners are not admissible. Internal code comments are governed by the comment discipline instead: extensibility or guard rationale mentioning the future is fine there; parking owed work is not. Scope, class catalogue, and boundary cases: [`ai/topics/no-future-extensions.md`](ai/topics/no-future-extensions.md); [`audit-no-future-extensions`](ai/skills/audit-no-future-extensions/SKILL.md) sweeps for violations.
- **Bugs vs. input errors: distinguish them in code.** Best of all is making illegal states unrepresentable at the type level. When the type system can't carry the constraint: input errors (bad user source) return a structured `Error` with a span and a message; internal contracts believed unreachable panic — typically `unreachable!("…")` with a message naming the earlier-phase contract. The user should never be left puzzled as to whether an error is a user error or a bug.
- **Debug-only surfaces are internal.** Debug, profiling, and timing-only features must use `kio debug ...`, `KIO_DEBUG_...` environment variables, or `--debug-...` command-line arguments. Document those options in `AGENTS.md`, `ai/topics/`, or implementation-internal comments — not in public `specs/` or `docs/`.
- **Versioning.** There is a single repo-wide version number, mirrored in every subproject's manifest and named in `README.md`. The canonical list of mirror points lives in `ci/checks/repo-lint/version-check.sh`, which CI runs to assert agreement. When the version bumps, update every mirror in the same change. When a new subproject joins the repo, append its manifest to `ci/checks/repo-lint/version-check.sh`'s mirror list at the same time. License metadata mirrors the same way: every subproject manifest carries the repo's `MIT OR Apache-2.0` SPDX expression, asserted by `ci/checks/repo-lint/license-check.sh` — a new manifest joins both scripts' lists in the same change.
- **Commits, sign-off, and push.** Every commit that reaches a pull request must end with a `Signed-off-by: Name <email>` trailer (the Developer Certificate of Origin sign-off) using a real identity — a GitHub DCO check rejects any PR with an unsigned commit — but an agent must **not** add that trailer on its own: signing certifies the DCO on the user's behalf, so do it only when the user explicitly asks. Pushing is likewise explicit: push **only** when the user asks, never as an unprompted follow-on to other work, and **never push a range that isn't fully signed off** — if asked to push unsigned commits, stop and report; do not silently sign them to make the push possible. Full DCO text and workflow: [`CONTRIBUTING.md`](CONTRIBUTING.md).
- **Repository automation is portable by default.** Do not introduce or deepen an OS-specific dependency in a shared script; existing violations remain defects, not precedent. State the applicable platforms and evidence for an automation change. Details: [`ai/topics/local-tools.md`](ai/topics/local-tools.md) § Script portability.
- **Run top-level Cargo commands in tracked repository workspaces through `ci/cargo.sh`.** Use `sh <repo-root>/ci/cargo.sh ...`; it preserves the caller's directory and arguments and acquires resources only in `work -> cargo -> compiler` order, with the capacity-one `cargo` resource present only when `KIO_CI_SERIALIZE_CARGO=1`. Run from the owning workspace (`<repo-root>/kio-rs` for compiler work) or pass its manifest. A scheduled caller reuses `work`; standalone Cargo takes none. Cargo's own subprocesses, emitted/fixture crates, and public host instructions use direct Cargo and never reacquire repository resources. Otherwise bare Cargo in a tracked workspace is reserved for stated wrapper diagnosis or repair. Mechanics: [`ai/topics/local-tools.md`](ai/topics/local-tools.md) § Scheduler-native Cargo serialization.
- **Don't bypass or break a configured compiler cache.** Do not clear `RUSTC_WRAPPER` or redirect ordinary builds to a throwaway cache; repair or report a stale wrapper. **Before the first build or `ci/all.sh`, export `SCCACHE_IDLE_TIMEOUT=0` and run `sccache --dist-status >/dev/null`** — `--show-stats` is not a liveness check. The scheduler's isolated generic readiness hook rechecks explicit wrappers, but a wrapper hidden in Cargo configuration still needs this session check; never stop or restart the daemon during a build. Fingerprints and recovery: [`ai/topics/local-tools.md`](ai/topics/local-tools.md) § Compiler cache.
- **Before running local CI, read [`ai/topics/local-ci.md`](ai/topics/local-ci.md) and choose the narrowest coverage that gates the change.** `ci/all.sh SAMPLE_IMPL` is the baseline broad gate: regular goldens and direct Prime run whole; dynamic Prime samples 50 cases per bucket. Every new or behaviorally edited golden uses anchored exact `FULL_IMPL_MATRIX --all-cases` filters without conflicting case policies or raw harness sampling overrides, unless inherently single-implementation. Changed source bytes alone do not establish a behavioral edit: reviewed mechanical syntax migrations and regenerated shared dependencies use a canonical-owner classification, transformation-appropriate equivalence evidence, unchanged case contracts, bounded exact full-matrix risk representatives, and normal harness coverage (`SAMPLE_IMPL` for matrix cases). Classify actual compiler/backend interactions per affected slice, not merely because compiler changes share the batch; diagnose uncertain rows and broaden on concrete uncovered risk or divergence. `FULL_IMPL_MATRIX` selects impls, not cases. Before launching an effectively corpus-wide full matrix, aggregate the scope across commands, explain why sampling plus representatives is insufficient, and obtain explicit user direction; long exact lists or split commands do not bypass this checkpoint. Case coverage is separate; narrowing still runs case-binary checks. Normally retain the dynamic-Prime sample and add exact tests for affected behavior. Require `--case-coverage=dyn-load-prime:all` when changes to dynamic loading, interpretation, or shared execution have sufficiently broad effects that focused tests plus sampling cannot adequately cover the risk; state that risk explicitly. A codegen change or a closeout gate alone does not require full dynamic coverage. Omit `--jobs` and `--compiler-jobs` ordinarily and when measuring defaults; numeric values are fixed overrides. Direct phase-path checks supply every impl's `prime-kio=<bin>`. Never run `ci/all.sh` through `nohup`; use [`ai/topics/local-ci.md`](ai/topics/local-ci.md) § Durable broad runs. Selector syntax: [`TESTING.md`](TESTING.md) § Local iteration.
- **Delegated and background work remains owned until reconciled.** Do not send a terminal response merely because no synchronous action is ready while a delegated agent, gate, monitor, or other launched task is still expected to advance the user's requested work. Keep coordination live with event-driven waits; consume completions and failures promptly; after each completion and at least hourly reconcile owners, processes and logs, durable checkpoints, free capacity, and next actions without rapid no-change polling. A missing approval blocks only actions that depend on that approval: continue safe read-only work, validation of frozen authorized changes, and other already-authorized tasks. Before sending a terminal response, every launched task must be completed and acted on, explicitly canceled, or blocked on identified user or external input and reported. A status request may uncover and repair a miss, but must not be the normal completion signal. Lifecycle mechanics: [`ai/topics/local-performance.md`](ai/topics/local-performance.md) § Delegated and background work lifecycle.
- **Tooling friction feeds back into the instructions.** When reality contradicts this file, a topic, or a skill — a documented command fails, a flag or path has moved, a needed step turned out to be missing — propose an update to the owning file in the same session rather than silently working around it. Corrections verifiable from the repo alone land with the session's change; experience-derived guidance (workarounds, new advice) is surfaced to the user for review first. Either way the update must pass the portability filter in [`ai/topics/no-leak.md`](ai/topics/no-leak.md): true on a fresh clone on any machine, phrased from symptoms, never encoding the current machine's state or one maintainer's workflow.
