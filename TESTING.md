# Testing strategy

Strategy and decision tree for tests in the Kio repo. For *how* to run the harness and what files a test case contains, see [`test-data/README.md`](test-data/README.md). For exit-code categories asserted by tests, see [`specs/exit-codes.md`](specs/exit-codes.md).

## Philosophy

**Cross-implementation by default.** Every language, diagnostic, runtime, or public-API test that can be expressed through a fixed independent runner protocol is a golden run through the cross-implementation harness, not an in-tree Rust test or a backend-specific artifact script. The runner uses only the documented public host interface, so its native compile/load/run is the default ABI oracle. The harness asserts observable behavior (exit code, stdout, and the case's stderr policy) and exit-code *category* per [`specs/exit-codes.md`](specs/exit-codes.md), not message text. A backend-specific public-host fact that the ordinary runner cannot naturally and independently demonstrate, or a durable output-layout fact, lives in the emissions corpus; private implementation invariants live in unit or mutation tests. A negative public-CLI golden that pins a category must isolate that defect rather than rely on precedence among multiple independent errors.

**Multiple layers, each catching what the layer above can't.** The layers below exist for redundancy. Passing one isn't a substitute for passing the others — a Rust unit test that exercises the typer's internal invariant is not a replacement for a golden that pins observable behavior, and vice versa.

## Test layers

Listed most-specific to most-general. Each says what it catches, what it doesn't, and where to run it.

- **Rust unit tests in `kio-rs/`** — `( cd kio-rs && sh ../ci/cargo.sh test )`. Internal invariants of the typer, parser, resolve, desugar, DNF, and elaborator passes. Useful for cases where a public-CLI test would be cumbersome to set up (e.g. property tests on type ASTs via `proptest`). Live next to the code they exercise.
- **Hand-written goldens under `test-data/goldens/<NN_category>/`** — `ci/run-tests.sh`, driven by `ci/checks/orchestrators/golden-tests.sh`. Pin specific observable behavior across implementations. Bucketed by exit-code category: `00_success`, `02_cli_error`, `11_parse_error`, `12_use_error`, `13_name_resolution_error`, `14_type_error`, `15_elaborator_error`, `16_totality_error`, `20_bridge_error`, `30_dependency_error`, `40_build_error`, `50_test_failure`, `60_fmt_check`, `80_*` / `81_*` / `82_*` (the `kio sig status` CI-gate tier: 80 unrecorded-incompatibility, 81 stale-but-compatible, 82 recorded-unsealed-break), and `90_runtime_exit` (built-and-run cases whose `expected.exit` is the program's own runtime code, not a compiler category — see [`specs/exit-codes.md`](specs/exit-codes.md) § Runtime exit codes). The bucket asserts the case's expected exit category — message text is not part of the assertion — so a negative public-CLI case contains no unrelated independent error that could validly determine another exit code.
- **Backend emission cases under `test-data/emissions/<backend>/<case>/`** — `ci/checks/orchestrators/emissions-tests.sh`. One-backend, success-only evidence for either a public generated-host fact that the ordinary fixed runner cannot naturally and independently demonstrate (`HOST_INTERFACE`: a host independently determined from the backend spec compiles and runs against the artifact) or a durable specified/measured artifact fact (`ARTIFACT_SHAPE`). Every case carries exactly one marker. A case that merely duplicates a runner-proven API contract is misplaced. This corpus is not a home for private compiler invariants or incidental generated text, and it supplements rather than satisfies the runtime cells in [`audit-backend-completeness`](ai/skills/audit-backend-completeness/SKILL.md). Contract: [`test-data/emissions/README.md`](test-data/emissions/README.md).
- **Generative tests via `ci/infra/kio-gen-rs/`** — `ci/checks/orchestrators/generative-tests.sh`. Seeded Kio test cases driven through the full pipeline. Catches integration regressions hand-written goldens miss. Failures get hand-promoted into goldens via the seed printed on every run.
- **Castles under `test-data/castles/`** — `ci/checks/orchestrators/castle-tests.sh`. Larger composed Kio programs (algorithms, toy games, parsers, simulations, puzzle solvers) run end to end through the standard `run.args` runner path. Success-only: every castle exits `0`. Castles are the integration layer — realistic composition that catches regressions both minimized goldens and generated Kio' programs miss, because no minimized golden or random Kio' program assembles the same combination of features a hand-written small program does. The orchestrator samples by default (printing the effective seed and the selected castle names so any failure reproduces; `--all-cases` runs the whole corpus — see § Case coverage). A castle that exposes a Kio bug keeps its natural source shape; the bug is fixed in the same change and pinned by a focused regression golden under `test-data/goldens/`. See [`test-data/castles/README.md`](test-data/castles/README.md) for the corpus contract.
- **Contributed cases under `test-data/contrib/`** — `ci/checks/orchestrators/contrib-tests.sh`. The external-contribution lane ([`CONTRIBUTING.md`](CONTRIBUTING.md) § Contribute an example program or library): small, self-contained cases, each in a flat directory `<github-username>-<issue#>` named after its contributor (only that contributor may open follow-up PRs against it). A case is one of three shapes — an example **program** (`run.args`), a **library** (`run.test-only`: `kio test` + `kio build`, no runner, with at least one required `equiv` law), or a **bug reproducer** marked `KNOWN_FAILING` (expected to fail: the run prints a `warn` line and the gate stays green, and a stale marker — a case that starts passing — fails so it gets cleaned up). A `run.sh` case is also allowed but runs on a PR only after a maintainer applies the `test-contrib` label. The orchestrator samples which cases build and run (`--all-cases` runs the whole corpus — see § Case coverage), because the lane grows from outside the repo without bound and is the regression net for nothing: a contrib case that exposes a bug is pinned by a focused golden. A `KNOWN_FAILING` reproducer is never sampled out, so the stale-marker gate below always runs. A maintainer-owned `example-0` keeps the harness exercised when no contribution is open. The corpus contract is deliberately relaxed relative to goldens / POCs / castles (natural Kio a user would write; see [`test-data/contrib/README.md`](test-data/contrib/README.md)); the orchestrator validates the *structural* contract mechanically (naming, layout, required files, file allowlist), while the quality bar is a matter for review. When a maintainer fixes the bug a `KNOWN_FAILING` case reproduces, they remove the marker and pin the fix with a focused regression golden under `test-data/goldens/`.
- **The Kio' verifier (`ci/infra/kio-prime-check-rs/`).** Independent recursive-descent parser for [`specs/prime.md`](specs/prime.md) § Grammar. Used as an oracle against `kio-rs`'s emitted Kio' (kio-prime round-trip check) and against the `IS_KIO_PRIME` biconditional on every case. The redundancy is the point — bugs in the main parser don't propagate to the verifier.
- **The `dyn_load_prime` interpreter differential (`dyn-load-prime@kio-prime`)** — `golden-tests.sh`'s third impl bucket, gated by the per-case `DYN_LOAD_PRIME` marker (run-tests' `--dyn-load-prime-only` filter). A marked golden is built with `kio build kio-prime` and the **whole** emitted image tree — every module, host module, and the `.pkg.kio` manifest — is fed to `dyn_load_prime`'s `load_package` and run by its `prime_eval` CEK interpreter under QuickJS (`kio-test-runner-dyn-load-prime`), asserting stdout and exit agree with compile-and-run. Where the verifier is a *syntactic* oracle over emitted grammar, this is a *semantic* one: a Kio-authored interpreter and the compiled backends must agree on every marked program. The dyn runner resolves the same exact `RunnerProtocol` as the backend runners and projects that contract into the Kio driver. `compile-only` stops after `load_package`; loading checks structural, import, host-contract, and export-contract edges but trusts function-body typing. `construct-only` instantiates the exact empty-host package without invoking an export. Every main protocol instantiates its selected exact host contract and invokes `main` in its exact declaring module through the loaded surface; supported export protocols instantiate the same way and drive their fixed surface scripts. Before evaluation, the driver compares the image's complete runtime host-function seed inventory with the selected protocol by exact descriptor and value-group shape; `instantiate` additionally checks retained bridge host types and functions against the adapter. The guest's host calls then flow through canonical capability bodies, while three driver-local callback descriptors remain isolated implementation details for callback-valued scripts and host results. At runtime, `make_lit` receives the image's exact `Host_type`, resolves its qualified identity against the selected protocol, and uses that exact host type's `HostTypeFixture`; conditionals pass the exact host type and opaque scalar to `test_bool`, leaving interpretation to the host capability rather than a role lookup. The marker is **derived, not curated**: a `00_success` case is eligible when it runs the standard `run.args` path with expected exit `0`, has a root manifest build block, and selects a protocol with a complete dyn-load-prime adapter. An eligible case carries the marker plus a `target kio-prime` block. `ci/checks/repo-lint/dyn-load-prime-coverage.sh` consumes the shared protocol registry's canonical support classification and rejects marker/build-target drift; exact entry, descriptor, group, and host-contract compatibility remain runtime questions rather than a second shell parser or typechecker. The rare eligible case the differential genuinely must not run carries `SKIP_DYN_LOAD_PRIME` instead, whose file content must state the reason (the lint rejects an empty one). Like the verifier bucket, it is single-impl and never trimmed by `--impls=SAMPLE_IMPL`.
- **Per-backend test runners (`ci/infra/kio-test-runner-rs/`).** One bin per executable backend — `kio-test-runner-js` evaluates emitted ES modules under rquickjs (Rust bindings around the QuickJS C engine), `kio-test-runner-ts` runs the TypeScript backend's byte-identical `<pkg>.js` through that same JS engine, `kio-test-runner-python` imports emitted Python modules with a synthesized host object, `kio-test-runner-java` compiles the emitted typed Java facade with a synthesized typed `Driver.java`, `kio-test-runner-rust` runs the emitted Rust crate via direct `rustc` invocations, and `kio-test-runner-{go,swift,haskell}` compile and run the emitted package with a synthesized driver. The runner is per *backend*, not per compiler: a runner doesn't know which compiler produced its artifact. `ci/run-tests.sh` picks the right runner via the `target=` key on each `--impl-def=` row; exec cases that route through `$KIO_RUNNER` are parametric over `KIO_TARGET`. The optional `prime-kio=` key supplies that row's separately-built reduced Kio' compiler and is mandatory when an enabled check declares `# REQUIRES: prime-kio`. Golden-owned code passes generated host artifacts to these fixed protocols opaquely; a backend-specific host fact belongs in `test-data/emissions/` only when the ordinary runner cannot naturally and independently demonstrate it. The bins share a `TestRunner` trait and structured protocol/rendering helpers in files under `src/shared/`, included into each bin via `#[path]` (no lib facade) — see [`test-data/README.md`](test-data/README.md) and [`ci/infra/kio-test-runner-rs/README.md`](ci/infra/kio-test-runner-rs/README.md) for the layout.
- **Per-case checks (`ci/checks/per-case/`)** — `fmt-canonical.sh`, `dep-canonical.sh`, `prime-marker.sh`, `kio-prime-roundtrip.sh`, and the rest of the directory. Run before each case's normal execution. Catch invariants the golden output alone can't (every tracked `.kio` file under `workdir/` is at `kio fmt`'s fixed point; a committed materialized dependency tree being byte-for-byte what `kio dep fetch` regenerates; the IS_KIO_PRIME marker matching reality; byte-identical target artifact trees from direct compilation and from full-compiler Kio' emit followed by the reduced compiler). `kio-prime-roundtrip.sh` cold-builds both paths with Kio caches bypassed, validates every emitted regular module with the independent Kio' verifier, and compares generated file paths and raw bytes before any host compiler runs; a successful direct target build is the eligibility test, so custom-script and dependency cases participate whenever they produce that target, except that the harness excludes `KNOWN_FAILING` cases from every per-case check. Compile-only `runner=SKIP` rows still run impl checks unless a check declares `# REQUIRES: runner`. Opt out of `fmt-canonical` with `SKIP_KIO_FMT_CHECK` for cases whose subject is deliberately non-canonical input (fmt round-trip fixtures, parser-acceptance fixtures). A case-binary-routed check attributes its pass/FAIL to a synthesized `<tag>@<binary>` impl row (default tag `invariants`; a check may declare a different one with a `# SYNTH-TAG: <name>` marker), reported on its own summary line rather than as a backend — these synthesized rows never enter the `--impls=SAMPLE_IMPL` rotation (which picks one *real* backend per case). Every current case-binary check uses the default tag, so their verdicts roll into a single `invariants@<binary>` row.

  For expected-success cases, the roundtrip check requests the direct target and Kio' target in one multi-target command. If that command fails, the check replays the two legacy builds fail-closed: an inapplicable direct target still skips, a Kio' failure stays fatal, and two successful legacy builds expose a combined-build regression rather than hiding it. Nonzero cases retain the legacy sequence. Normal case execution retains its own test/build/runner path.

  Every `equiv` block is discharged by `kio test`. The standard `run.args` path runs `kio test` as a build prerequisite (`ci/run-tests.sh` `execute_case`) before it reads `run.args`, so every `run.args` case — empty args or not — discharges its `equiv` blocks automatically, and a discharge regression fails that case. A `run.test-only` case (a library, no `main`) is the harness-owned path minus the runner — static validation only: `kio test` + `kio build`, no runner, no protocol, nothing executed (a case needing its program run uses `run.args`) — so it discharges its `equiv` blocks the same way. A `run.sh` case opts out of the harness-owned path entirely (it runs its own `kio dep fetch` / `kio check` / `kio test` as its subject requires; a dependency-bearing case regenerates its committed tree with `kio dep fetch` before the run, and a few git-dependency cases assemble and fetch a dependency at run time), so a `run.sh` golden whose package can declare `equiv` **must invoke `kio test` itself wherever discharge is reachable**. The `ci/checks/repo-lint/equiv-discharge.sh` CI gate enforces that obligation, exempting cases whose `expected.exit` is a pre-discharge error (parse / type / elaborator / dependency / …) where `kio test` cannot reach discharge (`audit-corpus` § 7 is the manual backstop). The POC and castle corpora carry the same obligation through their own `kio test` lines (`audit-corpus` §§ POC 6, Castle 7).
- **Highlight corpus (`test-data/highlight-corpus/`)** — `ci/checks/orchestrators/highlight-tokens.sh` plus `ci/checks/orchestrators/highlight-agreement.sh`. Lexer-level tokenization fixtures, locked against the canonical token-kind vocabulary. Each fixture pairs `source.kio` with the `kio debug tokens` JSON dump in `expected.tokens.json`; the runner diffs and supports `-u` for intentional updates. `highlight-agreement.sh` adds a second pass that runs the same fixtures through the tree-sitter grammar (`tools/tree-sitter-kio/`) and the TextMate grammar (`tools/textmate-kio/`) and asserts cross-tokenizer agreement. Positive classifications match `kio debug tokens`; provider-dependent bracket runs and bracket-led call arguments may remain silent under an exact aggregate span because those grammars do not have the compiler's selected operator scope.

## Stress and semantic coverage

Keep routine semantic checks small; use larger workloads when depth or volume
is itself the subject, such as exposing a host-stack overflow. These are
different coverage claims: a compact case can check execution semantics without
proving deep-stack safety.

A stress case may use `SKIP_DYN_LOAD_PRIME` when interpreting its large workload
is prohibitively expensive. This excludes only the additional interpreter
differential, not its applicable backend runs or Prime validation. Before using
the exception:

- Establish the cost with bounded measurements and investigate unexpected
  failures or scaling. A timeout alone does not establish that the interpreter
  is correct; do not use a cost exclusion to conceal incorrect results, crashes,
  or an identified interpreter defect.
- Retain focused dynamic coverage of the same semantic shapes at practical
  sizes. Existing cases may supply it; otherwise add a compact companion. Keep
  the original stress coverage on applicable backends, including its causal
  regression evidence. Do not claim the compact case proves the excluded depth.
- Replace `DYN_LOAD_PRIME` with a nonempty `SKIP_DYN_LOAD_PRIME` explaining the
  stress workload and its excessive interpretation cost, and identifying the
  retained dynamic semantic cases. Preserve diagnostic measurements in the
  validation record; the marker's explanation must be portable.

Prefer shared source with different inputs over independently maintained copies
of a program. Use existing fixture and dependency mechanisms where practical;
the split does not require a new runner or a different JavaScript engine.
Reassess an exclusion when the workload or interpreter changes materially.

## Cross-implementation discipline

Why tests run through `--impl-def=` rather than directly in cargo:

- **More than one implementation of Kio exists** — `kio` and `kio-prime` — and the harness treats the implementation list as open (`ROADMAP.md` tracks direction). Tests need to assert behavior that's implementation-agnostic.
- **Message text is not portable.** Two implementations producing parse errors will phrase them differently; only [`specs/exit-codes.md`](specs/exit-codes.md) categories are part of the contract. Cases carry `expected.stderr.grep` only for stable stderr subject facts: one POSIX ERE per line, every regex must match somewhere in actual stderr while allowing extra warnings or notes. When no stable stderr fact beyond the exit category matters, prefer `expected.stderr.ignore`; the bucket plus `expected.exit` already assert the category. Exact `expected.stderr` is rare and reserved for whole-stream contracts where extra stderr would itself be a regression. The three stderr policy files are mutually exclusive: see [`test-data/README.md`](test-data/README.md) § Golden test case layout.
- **Adding a new implementation** means adding one entry to the implementations list in `ci/checks/orchestrators/golden-tests.sh` (and similar for generative tests). All existing goldens then run against the new impl. Expected divergences are accommodated via per-case markers (`IS_KIO_PRIME`, `expected.stderr.grep`, `expected.stderr.ignore`); unexpected divergences are bugs.
- **A golden runs on every applicable implementation/backend.** A case's `build { ... }` block declares every target that can express the language/runtime behavior; the harness skips an impl whose target the block does not name. A golden is never made single-backend merely so its `run.sh` can inspect emitted host files — that subject belongs in `test-data/emissions/<backend>/`. Golden-owned code may only give an opaque artifact directory to a fixed runner protocol. The direct-artifact exception is Kio': it is a specified backend-neutral phase representation, so a case may read or assemble Kio' when that representation or `dyn_load_prime` is the subject; generic harness-owned phase checks such as the Kio' round trip remain valid. A target-independent compiler, debug-instrumentation, or CLI case may use one routing target solely to reach the shared compiler phase it observes; it makes no backend claim only when it neither consumes the generated artifact nor asserts backend behavior. Omitting an applicable target to dodge an emitter gap is forbidden; leave the failing language/runtime golden in place and fix the emitter.

This split prevents tautological backend tests. `HOST_INTERFACE` emission cases compile host code determined independently from the public backend spec; the narrow mechanically-wide exception in the corpus contract may generate repeated host source solely from fixed checked-in parameters, never from emitted output. `ARTIFACT_SHAPE` cases assert only durable specified or recorded-measurement facts. Exact private helper names and no-filesystem invariants stay in unit/mutation tests, and incidental private assertions are deleted rather than migrated.

An unknown build-target diagnostic uses `UNKNOWN_BUILD_TARGET` to route its
custom `run.sh` independently of the intentionally invalid target name. It
requires expected exit 40 and at least one declared target. Normal target
eligibility remains unchanged for unmarked cases; implementation and case
sampling still apply to marked cases. These rows assert a compiler diagnostic,
not emitted host behavior. See the [marker contract](test-data/README.md#golden-test-case-layout).

## Decision tree — "I want to test X. Where does it go?"

- **New surface form** (e.g., a new sugar form, a new keyword) — golden under `test-data/goldens/00_success/` exercising the form end-to-end; cargo test if a typer/parser internal invariant warrants direct coverage; consider whether the generative-test mutator should learn the form.
- **New error category** — add the exit-code spec entry in [`specs/exit-codes.md`](specs/exit-codes.md) first, then a golden under the matching `<NN_>` bucket asserting the category fires.
- **Codegen change with language/runtime consequences** — golden(s) under `test-data/goldens/00_success/` checking run output and exit status through fixed runner protocols. Malformed host code surfaces when the runner loads/compiles the opaque artifact; the Kio' phase-path differential remains a generic harness-owned check.
- **Generated host interface or ABI contract** — first express it as a fixed runner protocol and a cross-implementation golden; the runner's ordinary native compile/load/run is the default public-API oracle. Use one `HOST_INTERFACE` case under `test-data/emissions/<backend>/<case>/` only when a backend-specific host operation or negative/source-level relationship cannot be demonstrated naturally and independently by that runner. Mechanically-wide host source may be generated only from fixed checked-in parameters under the corpus contract.
- **Generated filesystem contract** — use one `ARTIFACT_SHAPE` case under `test-data/emissions/<backend>/<case>/` only for a durable spec fact or a portable proxy backed by a recorded measurement. Use neither corpus for exact private helper spellings or no-filesystem compiler invariants; cover those in unit/mutation tests, and delete incidental private assertions.
- **FFI runtime behavior** — cross-backend golden(s) under `test-data/goldens/00_success/` named `ffi_*`, with `run.args` carrying `--protocol` and the protocol name as separate lines. Protocols live in `ci/infra/kio-test-runner-rs/README.md` and `src/shared/protocol.rs`; add the protocol implementation, README table row, and per-backend runner support in the same change. Keep `workdir/` Kio-only; the protocol owns host-language-native host / bridge driving. `run.args` cases use the standard harness path: run `kio test` first unless `IS_KIO_PRIME` is present, build `workdir` for `$KIO_TARGET`, then invoke `$KIO_RUNNER` with the listed args followed by `out/$KIO_TARGET`; the Kio' phase-path check compares the two generated target trees before that runner step. `$KIO_RUNNER` is the single corpus-facing runner handle: its harness-owned proxy injects the package name only for one discoverable package in a regular, non-symlink top-level manifest and only when the invocation has no explicit split or `=` `--package-name`; other custom scripts pass ordered descriptors through that same handle. A case with a configured target namespace records the portable harness argument `--artifact-namespace <target-id>=<namespace>`; `ci/run-tests.sh` selects the current target's value and gives the runner a target-local ordered artifact descriptor. The fixed runner is the default host-source usability proof; only a backend-specific relationship it cannot naturally and independently demonstrate receives separate `HOST_INTERFACE` evidence, never case-specific protocol adaptation.
- **Package coexistence** — two complementary goldens drive the `coexist`
  protocol. `test-data/goldens/00_success/ffi_two_packages_coexist/` contains
  **two** sibling packages identical up to their names (same module paths,
  export and host-fn leaves, and shapes), so every name that could collide does.
  `test-data/goldens/00_success/ffi_same_package_namespaces_coexist/` uses two
  separate manifest roots with the same package name and byte-identical modules,
  building each for one backend under a distinct configured artifact namespace.
  Each custom `run.sh` runs
  `kio test` and `"$KIO_BIN" build "$KIO_TARGET"` in both roots, then gives the
  runner two ordered artifact descriptors (`--package-name`, an optional
  target-local `--artifact-namespace`, and the matching positional output
  directory). The runner hosts both artifacts in one host program and
  interleaves calls into them, jointly exercising namespace-derived symbol
  coexistence ([`specs/backends/README.md` § The package facade](specs/backends/README.md#the-package-facade)
  § Coexistence) and instance isolation (§ 4 there). Extending the property to
  a new backend means implementing the `coexist` protocol and adding that
  backend's target to both sides of both goldens.
- **Spec change** — check whether existing buckets cover the new spec rule. If not, add coverage in the bucket whose exit code the new rule would produce. A spec change without a corresponding test is a contract assertion without enforcement.
- **Refactor (no behavior change)** — no new test. Existing tests guard against regressions. The PR description should call out which tests gave confidence the refactor is behavior-preserving.
- **Bug fix** — regression golden first (the case must fail before the fix and pass after), then the fix. The golden lives in whichever `<NN_>` bucket matches the bug's observable category.
- **Coverage signal from `reports/`** (a mutation survivor, a fuzz finding, a coverage delta) — fix at the layer that produced the signal, **and** twin user-visible shapes with a golden. The mutation harness runs only `cargo test`, so the killer for a mutation survivor is always an in-crate kio-rs test; when the pinned behavior is also observable through the public surface (an exit category, a diagnostic, an `equiv` verdict, runtime output), add a golden under the matching bucket in the same change so the behavior stays pinned across implementations, which no in-crate test does. Check the corpus for an existing case already pinning the shape first — the twin adds missing cross-implementation coverage, not duplicates. Internal-invariant gaps (slot arithmetic, memo internals, interner state) stay unit-test-only. A finding that exposes a real bug (a fuzz crash, a wrong result) follows the **Bug fix** row instead: regression golden first.
- **Unpinned user-visible behavior discovered** — by triage, review, code reading, or a question, with no change or report attached — treat the discovery itself like a coverage signal: add the golden in the matching bucket after checking for an existing case, with the same internal-invariant carve-out as above. A behavior worth wondering about is worth pinning; the corpus grows gap-driven, not only change-driven.
- **Tokenization or vocabulary change** — fixture under `test-data/highlight-corpus/` exercising the new shape, regenerated with `sh ci/checks/orchestrators/highlight-tokens.sh -u`. The canonical vocabulary is the `TokenKind` enum in `kio-rs/src/tokens.rs`; growing the vocabulary means adding a variant there and regenerating the fixtures in the same change.

## Harness impl-list parity

Every test harness that defines impls for `ci/run-tests.sh` (`ci/checks/orchestrators/golden-tests.sh`, `ci/checks/orchestrators/emissions-tests.sh`, `ci/checks/orchestrators/generative-tests.sh`, `ci/checks/orchestrators/kiodoc-tests.sh`, `ci/checks/orchestrators/poc-tests.sh`, `ci/checks/orchestrators/castle-tests.sh`, `ci/checks/orchestrators/contrib-tests.sh`, and any future harness with the same shape) keeps the *same shape* across harnesses: every Kio compiler / backend pair the repo ships shows up in each harness's `$ALL_IMPLS` declaration. When a new compiler or backend lands, update every harness's `$ALL_IMPLS` in the same change so the corpus exercises that compiler / backend everywhere it's relevant.

The exception is **deliberate narrowing**: a harness may scope itself to a subset when its subject doesn't exercise the omitted backend. `ci/checks/orchestrators/kiodoc-tests.sh` is js-only because doc snippets exercise `kio doc`'s markdown / typecheck path, not the backends; adding the rust impl there would do nothing but slow CI. `ci/checks/orchestrators/poc-tests.sh` omits the kio-prime impl because POC `run.sh` files invoke `kio test` (a surface-only CLI kio-prime rejects). Narrowing must be documented at the impl-list site (an explanatory comment near the `$ALL_IMPLS` declaration) so the next change doesn't silently un-narrow it.

Each harness's `$ALL_IMPLS` carries a short header comment pointing here. Adding a new harness with an implementation list means copying that header in.

The same parity discipline applies to the **verification passes** wired through the `--check=` pipeline rather than `$ALL_IMPLS`. Case-binary-routed checks such as `fmt-canonical.sh`, `dep-canonical.sh`, and `prime-marker.sh` produce synthesized rows; impl-routed checks such as `kio-prime-roundtrip.sh` and emitted-skin/cache checks contribute to a backend impl's verdict. `dep-canonical.sh` is wired into each language corpus that can carry a committed dependency tree — goldens, POCs, and castles. `kiodoc-tests.sh` wires no per-case checks. `castle-tests.sh` and `contrib-tests.sh` carry the source/phase checks appropriate to their contracts. `emissions-tests.sh` deliberately wires only source formatting and a runner tripwire: each success-only `run.sh` owns its backend build and public-host/artifact assertion, and accidentally falling back to an ordinary synthesized runner is a contract error. When adding a check, wire it into every corpus whose subject it actually governs rather than assuming all harnesses have the same evidence role.

## Local iteration

The golden, emission, and generative harnesses run every selected case against every applicable impl when asked for `--impls=FULL_IMPL_MATRIX` (an emission case itself names exactly one backend target). Case coverage is independent; add `--all-cases` to run all filtered cases, including the golden harness's sampled dynamic-Prime pass. This section documents selector syntax, not the per-change gate policy.

- **`--impls=SAMPLE_IMPL`** — for each case, pick **one** of its applicable impls at random per run. Each case selected by the independent case policy still runs (assuming it has at least one applicable impl), so the pass count stays the same; what changes is that backend divergence isn't exercised within a single run.
- **`--impls=FULL_IMPL_MATRIX`** — run every applicable impl for each case. This is the exhaustive matrix and is intentionally expensive.
- **`--impls=<impl>[,<impl>...]`** — restrict the candidate pool the harness even considers. Cases whose `build { ... }` block doesn't declare any of the surviving targets are skipped entirely.
- **Positional case-name filters after `--`** — POSIX EREs matched against case names, forwarded to `ci/run-tests.sh` (e.g. `sh ci/checks/orchestrators/golden-tests.sh --impls=kio@go -- '^00_success/my_case$'`). The golden, emissions, generative, POC, castle, and contrib orchestrators all accept them; a filter passed without the `--` separator is rejected with a hint naming the convention.

The matrix orchestrators accept one implementation selector per run: `--impls=FULL_IMPL_MATRIX`, `--impls=SAMPLE_IMPL`, or `--impls=<impl>[,<impl>...]`.

| You want | Run |
|---|---|
| One impl per applicable case | `sh ci/checks/orchestrators/golden-tests.sh --impls=SAMPLE_IMPL` |
| All applicable impls for filtered cases | `sh ci/checks/orchestrators/golden-tests.sh --impls=FULL_IMPL_MATRIX --all-cases -- '^00_success/my_case$'` |
| Focus on JS (every JS-applicable case on `kio@js`) | `sh ci/checks/orchestrators/golden-tests.sh --impls=kio@js` |
| Focus on Rust (every Rust-applicable case on `kio@rust`) | `sh ci/checks/orchestrators/golden-tests.sh --impls=kio@rust` |
| One emission case | `sh ci/checks/orchestrators/emissions-tests.sh --impls=FULL_IMPL_MATRIX -- '^rust/my_case$'` |

Notes:

- The `kio-prime@js` verifier bucket (`--prime-only` invocation in `golden-tests.sh`) runs an isolated `--no-default-features --features prime,cli,parallel` compiler, rather than the default-feature `kio-prime` binary; this keeps its dependency-command path genuinely surface-less. That bucket and the `dyn-load-prime@kio-prime` differential bucket (`--dyn-load-prime-only`) are always single-impl, so `--impls=SAMPLE_IMPL` never trims them. IS_KIO_PRIME-marked cases still get their Kio' grammar gate, on every invocation; DYN_LOAD_PRIME-marked cases run their interpreter differential when selected by the independent case policy.
- Failure reproduction under `--impls=SAMPLE_IMPL`: every pass/FAIL line names which impl was picked (the `[<impl>]` tag). Re-run the failing case with `--impls=<that-impl>` to reproduce deterministically.

`ci/checks/orchestrators/generative-tests.sh` accepts the same `--impls=` selector with identical semantics. It also accepts `--count=<N>` to scope the generated batch and `--seed=<N>` to pin the generator for reproduction.

`ci/all.sh` uses the same coverage choices but exposes them as required positional arguments: `sh ci/all.sh SAMPLE_IMPL` for one applicable impl per case, `sh ci/all.sh FULL_IMPL_MATRIX` for the full matrix when explicitly needed, or `sh ci/all.sh kio@js kio@rust` to forward a focused impl list to the matrix orchestrators. Its repeatable `--impl-verification=<scope>` axis adds a registered fixed verifier without changing ordinary implementation selection, while repeatable `--case-coverage=<scope>:<policy>` selects scoped cases without changing implementations. `ci/all.sh --gen-count=<N>` and `ci/all.sh --gen-seed=<N>` forward to the generative orchestrator as `--count=<N>` and `--seed=<N>`.

Work-unit and compiler concurrency are separate native scheduler resources.
`--jobs=<N>` controls how many scheduled corpus/CI units may be active; omission
uses `std::thread::available_parallelism`. `--compiler-jobs=<N>` caps top-level
Cargo, compiler-producing Kio commands, and native-runner, host-doc, and
custom-`run.sh` compiler invocations across participating sibling worktrees.
It does not count Cargo's individual `rustc` children. With no compiler
override, the scheduler uses paced, best-effort CPU/memory feedback within
live CPU and explicit fixed-capacity limits. This is adaptive admission, not
a per-command memory reservation or an OOM guarantee; see the
[omitted-capacity policy](ci/infra/kio-ci-scheduler-rs/README.md#omitted-compiler-capacity).
A numeric override is a fixed hard cap and is accepted by `ci/all.sh`,
`ci/run-tests.sh`, and each corpus orchestrator. `KIO_CI_SERIALIZE_CARGO=1` additionally takes the
scheduler's capacity-one `cargo` resource around a top-level repository Cargo
command; the global resource order is `work -> cargo -> compiler`. Omit
overrides and Cargo serialization in ordinary use; they reproduce or
deliberately constrain scheduling, not test coverage.

The harness's typed-module cache is invocation-scoped. Standard `run.args` and
`run.test-only` cases share one root. Custom `run.sh` cases receive isolated
per-case, per-implementation roots unless the regular golden orchestrator
selects a fixed reviewed cohort. `run-tests.sh` resolves that ID to its sibling
harness-owned path-and-Git-object manifest; listed scripts execute authenticated
snapshots and share a separate root, while byte-identical scripts at unlisted
paths remain isolated. This is internal harness configuration, not a case marker
or a `run.args` capability.

### Case coverage: how many cases run, not how many impls

Implementation coverage and **case** coverage are independent axes, and the flag vocabulary keeps them apart: anything naming `impl` (`--impls=`, `SAMPLE_IMPL`, `FULL_IMPL_MATRIX`, `--impl-verification=`) selects or augments *implementations*; anything naming `case` (`--sample-cases`, `--all-cases`, `--case-count=`, `--case-seed=`, `--case-coverage=`) cuts *cases*. Neither is ever spelled as a bare "sample". The two compose: `--impls=SAMPLE_IMPL --case-count=20` runs 20 cases per bucket, each on one random applicable impl.

What case narrowing does and does not scope is the part to internalize. A corpus pass spends nearly all its time in the **impl tier** — `kio build <target>` plus a host-language compile and run, per case per impl. The **case-binary tier** (the `# ROUTING: case-binary` checks an orchestrator wires: `fmt-canonical`, `dep-canonical`, `prime-marker`, and on goldens `warm-recheck-stable`) is pure-compiler and cheap. Sampling, numeric caps, and named sets scope the impl tier *only*: a narrowed-out case still gets its `cache clear`, its `dep fetch`, and every case-binary check **its own orchestrator wires** (see § Harness impl-list parity for who wires what — contrib omits `dep-canonical`, since a contrib case is self-contained by contract and carries no dependency tree to drift). So fmt drift, materialized-dependency-tree drift, and a broken `IS_KIO_PRIME` biconditional stay gated on the **whole filtered corpus on every pass**, however narrow the impl tier becomes. Only build-and-run coverage is traded away.

One case never narrows out: a **`KNOWN_FAILING`** bug reproducer. Its gate is that it *starts failing* to fail — a reproducer whose bug got fixed fails the run so the marker gets cleaned up — and that gate lives in the impl tier, while a `KNOWN_FAILING` case's case-binary checks are skipped by contract (it is expected not to build cleanly). A narrowed-out one would therefore run nothing at all, so sampling, numeric caps, and named sets all pin it into the impl tier.

The count is **per top-level bucket**, not per corpus. `test-data/goldens/` concentrates its cost in `00_success`; its error tiers are separate buckets. `test-data/emissions/` uses one top-level bucket per backend, so a cap of `1` selects one case for every available backend rather than one case for the whole corpus. A flat corpus (castles, POC, contrib) is entirely unbucketed. A cap of `0` is rejected: a green run that built and ran nothing is the opt-out `AGENTS.md` forbids.

Each corpus orchestrator accepts `--all-cases`, `--sample-cases` (its own default cap), `--case-count=<N>`, and `--case-seed=<S>`, and each carries its own default:

| Corpus | Default | Why |
|---|---|---|
| `golden-tests.sh` | regular/direct Prime: all; dynamic Prime: sampled (50) | The primary regression paths run whole; the separate dynamic differential uses a rotating sample. |
| `emissions-tests.sh` | all | The corpus is the focused backend-specific ABI/artifact gate; local runs cover every case. |
| `poc-tests.sh` | all | Small, and each POC backs a published `docs/poc/` case study. |
| `castle-tests.sh` | sampled (10) | Large and slow; exists to catch composition regressions over time, not on every commit. |
| `contrib-tests.sh` | sampled (10) | Grows without bound from outside the repo, and is the regression net for nothing: a contrib case that exposes a bug is pinned by a focused golden, which guards the fix from then on. |

**Goldens' verification passes use scoped policy.** `golden-tests.sh` invokes the harness for regular goldens and registered fixed-verification leaves. `--case-coverage=goldens:<policy>` is inherited by active leaves; a leaf override such as `--case-coverage=dyn-load-prime:smoke` wins. Explicit leaf policy outranks explicit root policy, which outranks global flags, which outrank defaults; argument order matters only within one scope. `sample` (global or scoped) uses 100 for regular/direct Prime and 50 for dynamic Prime; an explicit numeric cap applies unchanged to each affected group. `--all-cases` or `--case-coverage=goldens:all` restores full filtered coverage unless a more-specific explicit policy narrows it. `--case-coverage=dyn-load-prime:all` restores that leaf independently. `--impl-verification=dyn-load-prime` activates that fixed verifier when an explicit regular implementation list would otherwise omit it. The implicit dynamic default never activates a deselected verifier. Narrowing affects impl runs only; case-binary checks retain the full filtered cohort.

Mandatory new or behaviorally edited golden runs use anchored exact selectors with `--impls=FULL_IMPL_MATRIX --all-cases` and no conflicting global/root/leaf case policy or raw harness sampling override. Filters apply before sampling; a batch larger than the cap can otherwise silently lose implementation runs. Neither implementation selector alone disables sampling. Raw receiving-harness case options forwarded after `--`, such as `--sample-cases=N`, can also narrow the run; do not append them to mandatory full-case commands.

The broad gate normally retains the dynamic-Prime sample of 50 cases per bucket, supplemented by exact tests for affected behavior. Use `--case-coverage=dyn-load-prime:all` when changes to dynamic loading, interpretation, or shared execution have sufficiently broad effects that focused tests plus sampling cannot adequately cover the risk; explain that risk explicitly. An isolated host-backend change, a new runner operation, or a closeout gate does not by itself require full dynamic coverage. A new operation still needs its exact regression and relevant existing-operation controls, and every new or behaviorally edited golden retains the mandatory coverage above.

`ci/all.sh` exposes the same axis across all registered corpora: `--sample-cases` samples each corpus, `--all-cases` runs every case, and repeatable `--case-coverage=<scope>:<all|sample|N|named-set>` wins for a root or leaf. With no flag each corpus applies its local default above. The normal GitHub invocation is `sh ci/all.sh SAMPLE_IMPL --sample-cases --impl-verification=dyn-load-prime --case-coverage=dyn-load-prime:10`; implementation and case sampling are independent, with full coverage on either axis available by explicit dispatch. Dynamic-Prime eligibility is restricted to `00_success`, so the per-bucket numeric cap selects 10 cases total there. `--case-seed=<S>` pins seeded draws; named sets are checked-in manifests.

## Coverage tracking

The optional kio-gen coverage audit runs `cargo-llvm-cov` over the goldens harness twice (alone, then with a fresh kio-gen batch) and reports kio-gen's *additional* line coverage on top of hand-written goldens.

- **Measures:** kio-gen's contribution to overall line coverage on a 500-case batch.
- **Doesn't measure:** total coverage, per-test coverage, per-module thresholds.
- **No coverage gate in CI.** Coverage is a leading indicator of test gaps, not a contract; gating on it would incentivize test padding more than test quality. The trend is informational. If a future incident traces back to a measurable coverage gap, that's the signal to revisit the policy.
